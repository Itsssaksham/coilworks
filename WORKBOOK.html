How this system works, and why it is built this way

A vending fleet platform, taken apart. Every section answers three things: what the mechanism actually does, why this technology was chosen over the obvious alternative, and what would change if you swapped it.

MERN · MongoDB · Express · React · Node github.com/Itsssaksham/coilworks 32 end-to-end tests

Coilworks operates a fleet of vending machines. Machines report telemetry; the platform turns that into live fleet state, alerts, depletion forecasts, and route-ordered restock runs. The interesting part is not the CRUD — it is that four different MongoDB capabilities each solve a problem that would otherwise need a separate piece of infrastructure.

01The mental model

Hold four facts and the rest follows. Machines push, they are never polled — a controller in the field heartbeats every 30 seconds over an authenticated HTTP endpoint. Every write lands in MongoDB first, and the database is what notifies everyone else. The browser never polls either — MongoDB tails its own oplog and the server forwards those events down a WebSocket. Reads are computed, not stored — forecasts and routes are derived on demand from sales history, so there is no cache to invalidate.

02Follow one heartbeat

This is a genuine ordered trace — each step depends on the one before it. A machine sends one telemetry POST, and this is everything that happens.

  1. The machine authenticates as itself
    middleware/auth.js → requireMachine

    The request carries X-Machine-Key. The server hashes it and compares against the stored hash with timingSafeEqual, not ===. A machine key authorises writes for exactly one machine and reads nothing — so a controller pulled off a wall and dismantled gives up very little.

  2. The payload is validated, then appended
    routes/ingest.js → Telemetry.create

    A Zod schema rejects anything malformed with the offending field named. The reading is appended to the time-series collection. Nothing is updated — telemetry is history, and history does not change.

  3. Latest values are denormalised onto the machine
    routes/ingest.js → machine.save()

    Temperature, cash, signal, and status are copied onto the machine document. This is the write the dashboard actually watches. Without it, rendering a fleet list would mean one aggregation per machine.

  4. The rules engine runs against the new state
    services/alerts.js → evaluateMachine

    Temperature, power, jams, cash level, and every slot are checked. Alerts are keyed so a condition that persists stays one alert instead of one per heartbeat, and conditions that clear resolve themselves.

  5. MongoDB tells everyone, unprompted
    realtime/hub.js → Machine.watch()

    The change stream fires on the write from step 3, the hub forwards it to every subscribed socket, and React merges it into state. From heartbeat to pixel with no polling anywhere — and no message broker either.

03Why MongoDB and not PostgreSQL

The decision

Document store over a relational database

What we used

MongoDB 8, single replica set

Why

Honestly? Postgres would model this domain fine — arguably better, since slots and sales are relational in shape. The reason MongoDB wins here is not the document model, it is that four separate infrastructure needs collapse into one system: time-series storage, geospatial indexing, a change feed, and transactions. On Postgres that is TimescaleDB plus PostGIS plus LISTEN/NOTIFY or Debezium — three extensions and a lot more to operate.

The planogram also genuinely suits embedding: twenty slots that are always read and written with their machine and never queried alone.

What if you changed it

Postgres + Timescale + PostGIS: stronger referential integrity and a much better story for reporting joins. You would gain real foreign keys — right now nothing at the database level stops a sale referencing a deleted machine. You would lose the one-system simplicity, and the live feed becomes the hard part rather than a free one.

MongoDB without the replica set: the app does not start. That is not a stylistic preference — see the next section.

04Why the replica set is non-negotiable

This trips people up, so it is worth being precise. A replica set here is not about redundancy or failover — it is a single node. It is there because two features the app depends on are implemented on top of the oplog, and a standalone mongod does not keep one.

FeatureUsed forStandalone mongod
watch() change streams The entire live dashboard unavailable — throws on open
Multi-document transactions Atomic vend: slot decrement + sale insert unavailable — throws on commit
Time-series collections Telemetry storage works
2dsphere geospatial Restock routing works
How the app handles it

db.js runs hello at boot and checks for setName. No replica set means it refuses to start, naming the fix. The alternative — booting happily and serving a dashboard that never updates — is a far worse failure, because it looks like it works.

Practically this costs almost nothing. Locally it is one extra flag (--replSet rs0) and one rs.initiate(). On MongoDB Atlas even the free tier is a replica set, so there is nothing to configure at all.

05Why a time-series collection

The decision

Native time-series, not an ordinary collection

What we used

timeField: ts · metaField: machineId · granularity: minutes

Why

Telemetry is the highest-volume thing in the system: 16 machines every 30 seconds is 46,000 documents a day, and a real fleet is thousands of machines. A time-series collection buckets many readings for one machine into a single stored document and stores fields column-wise, which cuts storage several-fold and makes “last two hours for this machine” a contiguous read rather than a scattered index walk.

The second win is expireAfterSeconds. Old telemetry deletes itself. No cron job, no cleanup script, no table that quietly grows until someone notices.

What if you changed it

An ordinary collection: everything still works — you would add a TTL index and a compound index on {machineId, ts} and never notice a difference at 16 machines. At fleet scale you would notice: more disk, slower range scans, and TTL deletes competing with your writes.

What you give up by choosing it: real constraints, not theoretical ones. Time-series documents cannot be updated or deleted individually, and the meta and time fields are immutable. The seed script has to drop() the whole collection rather than deleteMany({}). If telemetry ever needed correcting in place, this would be the wrong choice.

06Why slots are embedded

The decision

Planogram embedded in the machine document

What we used

machine.slots[] — array of ~20 subdocuments

Why

The test for embedding is: is this data ever needed without its parent, and is it bounded? Here, no and yes. A slot has no meaning apart from its machine, nothing ever queries slots across machines, and a machine has twenty of them, not twenty thousand. One read gets the whole machine, and one write updates it atomically without a transaction.

What if you changed it

A separate slots collection: every machine read becomes a join, and the atomic “decrement this slot” becomes a second write to coordinate. You would gain the ability to query slots globally (“every A1 across the fleet”) without $unwind — which the forecast pipeline does anyway.

Where embedding would break: if slots grew unbounded, or if two writers updated different slots on one machine concurrently. The second is real — the current code reads the machine, mutates a slot, and saves the whole document, so two simultaneous vends on different slots can clobber each other. At one controller per machine that cannot happen. With a mobile app vending from the same machine, it could, and the fix is a targeted $inc on the positional element rather than a whole-document save.

07Why change streams beat polling

This is the decision that most shapes how the app feels, so it is worth seeing rather than reading.

The decision

The database as the event source

What we used

Model.watch() with resume tokens → WebSocket fan-out

Why

The alternative to polling is usually a message broker: publish to Kafka or Redis on every write, subscribe in the API. That works, but it introduces a dual-write problem — the database write and the publish can disagree. If the publish fails after the write commits, the dashboard is permanently wrong and nothing detects it.

Change streams read the oplog, which is the write. There is no second write to get out of sync, and no broker to run.

What if you changed it

Redis pub/sub: this is the actual upgrade path, and it is needed for a different reason — not correctness, but horizontal scale. The current fan-out is in-process, so two API instances behind a load balancer each see the change stream but only reach their own sockets. That is fine; what breaks is rate limiting, which is also in-process. Redis fixes both.

Kafka: right if telemetry needed replay, multiple independent consumers, or retention beyond the oplog. Here it would be a broker to operate for one consumer.

The trap this nearly fell into

A change stream that errors is dead, and the browser cannot tell — the page keeps rendering the last data it received, with a green “live” indicator over frozen numbers. That is worse than a crash, because it lies. The hub now tracks a resume token, reconnects with backoff, and pushes a health frame so the UI shows an amber stale state instead. If the token itself has expired past the oplog, it restarts from now and accepts the gap rather than retrying forever.

08Why WebSockets and not SSE

The decision

WebSocket over Server-Sent Events

What we used

ws, one connection per browser, topic subscriptions

Why

The client talks back. It sends subscribe to narrow which topics it wants, and the server sends ping frames to reap sockets that stopped answering — laptops that slept, connections a proxy half-closed. SSE is one-directional, so both would need a side channel.

What if you changed it

SSE: genuinely simpler, and it survives proxies better because it is ordinary HTTP. It also reconnects on its own with Last-Event-ID, which maps neatly onto resume tokens. If the client never needed to talk back, SSE would be the better call — this is the closest decision in the document.

Long polling: works everywhere, and costs a request per update per client — the polling problem with extra steps.

09Why WebSocket auth uses tickets

The original build had a real hole: /ws accepted any connection and streamed the whole fleet — machine locations, cash levels, stock. The REST API was behind a token; the socket was behind nothing.

Fixing it runs into a browser constraint: you cannot set headers on a WebSocket handshake. There is no way to send Authorization: Bearer. So the credential has to travel in the URL — and URLs end up in proxy logs, access logs, and browser history.

The decision

Single-use tickets, not the session token

What we used

POST /api/auth/ws-ticket → 30s, one-time-use token in the query

Why

The ticket is minted over the already-authenticated REST API, expires in thirty seconds, and is deleted the moment it is redeemed. A ticket sitting in a log is worthless by the time anyone reads it. A twelve-hour session JWT in the same place is a full account compromise.

What if you changed it

JWT in the query string: what most tutorials do. It works, and it puts a long-lived credential everywhere URLs are recorded.

Cookie auth: the browser sends cookies on the WS handshake automatically, so no ticket is needed — but then you own CSRF, and the API stops being usable from a non-browser client without a second scheme.

The Sec-WebSocket-Protocol trick: smuggles a token through the one header you can set. It works, and it abuses a header that means something else.

The real cost of tickets: they live in process memory, so a second instance cannot redeem a ticket the first one issued. That lands on the same Redis migration as everything else here.

10Why plain Express and not Next.js

The decision

Express API + a React SPA, served together

What we used

Express 5 · Vite-built React · one process, one container

Why

Two reasons, and the first is the honest one: MERN means Express. This project exists partly to be a real MERN application, and Next.js would make it a Next application that happens to use MongoDB.

The second reason is technical and holds up. This app needs a long-lived WebSocket server attached to the same HTTP server, plus a background timer sweeping for offline machines. Both want a persistent process that owns its own server instance. That is exactly what serverless-first frameworks are built to avoid.

The dashboard is also behind a login and updates continuously — there is no SEO to win and no meaningful first-paint content to server-render.

What if you changed it

Next.js: you would get routing, code splitting, and image handling for free, and immediately need somewhere else to put the WebSocket hub and the sweep timer — either a custom server (which gives up most of the deployment benefit) or a separate always-on service.

NestJS: the right answer as the team grows. Dependency injection, module boundaries, and a WebSocket gateway built in. At this size it is structure you are not yet being paid back for.

Fastify: meaningfully faster and a better validation story. The one thing it costs is that “MERN” stops being literally true.

“Why not just put it on Vercel?”

Worth answering precisely, because the obvious answer stopped being true in June 2026 — Vercel added native WebSocket support to its functions. So “serverless can’t do WebSockets” is out of date.

The constraint that still bites is different. A WebSocket on Vercel is pinned to one function instance for that function’s maximum duration, and terminates when it is reached. On the Hobby plan that maximum is 300 seconds, with no way to extend it — so a live dashboard would drop and reconnect every five minutes. Survivable, since the client already backs off and reconnects, but it is the least of the problems.

The real issue is that four things in this app hold state in the process, and serverless gives you many short-lived instances instead of one long-lived one:

What holds stateWhat happens on Vercel
WebSocket tickets (in-memory Map) Minted by one instance, redeemed by another — and routing to the same instance is not guaranteed, so most redemptions fail
Change streams + resume tokens Every instance opens its own three streams against Atlas, and each new one restarts from “now”, dropping the gap
The 30-second offline sweep A setInterval does not survive between invocations; Cron is minute-granularity at best
Rate-limit buckets Per instance, so the effective limit is N times the intended one

All four are fixable — signed short-lived tickets instead of a Map, Redis for fan-out and limits, a Cron route for the sweep. But that is the same Redis migration the rest of this document keeps pointing at, done to satisfy a platform rather than to serve users, and it trades away the single-process design for a live feed that is measurably worse. Render, Railway, and Fly all run the existing container unchanged.

The version that does make sense

Put the SPA on Vercel and the API on a host with long-lived processes. That plays to what Vercel is genuinely best at — CDN-served static assets and preview deploys — and leaves the stateful half where it belongs. The CORS_ORIGINS allowlist already exists for exactly this split.

11Why the AI loop is hand-written

The decision

A manual tool-use loop over the SDK's tool runner

What we used

Claude Opus 5 · six read-only tools · six-turn cap · trace returned to the UI

Why

The Anthropic SDK ships a tool runner that drives this loop for you, and it is the right default. Two things argued against it here: it is a beta surface, and the offline fallback needs the same shape. Owning ~40 lines keeps both paths symmetrical and makes the full trace available to return to the operator.

That trace matters more than it sounds. The assistant's answer is shown beside the exact queries that produced it, so an operator can check the numbers instead of trusting them.

What if you changed it

The SDK tool runner: less code, and per-turn hooks that cover approval gates and retries. Worth switching to once it is stable.

Giving the tools write access: the single change that would most damage this design. Every tool is read-only, so a prompt-injected answer can mislead a reader but cannot acknowledge an alert, edit a planogram, or dispatch a technician. Adding one write tool means the model's output becomes an action, and the whole thing needs a confirmation step and an audit trail.

Why thinking stays on

Both AI features run with thinking enabled at low or medium effort rather than disabled. Disabling it looks cheaper, but on Opus 5 it has a specific failure mode with tool use: the model can write a tool call into its visible text instead of emitting a proper tool-use block. The turn succeeds, the tool never runs, and nothing errors. Low effort with thinking on is both cheaper than it looks and considerably safer.

12The forecast, in one query

“Which slots will run out this week?” is the question the whole restock feature rests on. The naive version is a loop: fetch machines, then for each of twenty slots count its sales. Sixteen machines is 320 round trips.

It runs as one aggregation instead:

StageWhat it does
$unwind: "$slots"Turns one machine with 20 slots into 20 rows, so each slot is addressable
$lookup with a pipelineFor each row, counts only that slot's sales inside the window — correlated with let, not a blanket join
$addFieldsratePerDay = unitsSold / windowDays
$addFieldsdaysToEmpty = qty / ratePerDay, or null when the rate is zero
$matchKeeps rows emptying inside the horizon, plus anything already at zero
$sortMost urgent first — this is the restock priority order

The null is a deliberate choice. A slot with no sales in the window has an unknown rate, not a rate of zero, and reporting “empties in infinity days” would quietly hide a slot nobody has checked. Unknown is represented as unknown.

What if you changed it

Computing in application code: means pulling every sale over the wire to count them. The aggregation counts them where they live. Caching the result: tempting, and it buys you a staleness problem — every vend invalidates one row. It is fast enough to compute on demand, so there is nothing to invalidate. A better model: the real weakness. A trailing average cannot see a holiday, a heatwave, or a site closure. Exponential smoothing or a day-of-week seasonal factor would be the honest next step.

13The routing algorithm

Once you know which machines need stock, you need an order to visit them in. That is the travelling salesman problem, which is NP-hard — so this does what production systems do and takes a good answer fast instead of the best answer eventually.

Step one, nearest neighbour: start at the depot, repeatedly go to the closest unvisited stop. Fast, and reliably mediocre — it commits to cheap early hops and pays for them at the end, leaving a path that visibly crosses itself.

Step two, 2-opt: take any two points in the route, reverse the segment between them, and keep the reversal if the total got shorter. Repeat until nothing improves. Every crossing is one such reversal away from being removed.

What if you changed it

Nearest neighbour alone: a visibly worse route for no saving worth having. An exact solver: optimal, and the runtime explodes past about twenty stops. A real routing API (Google, OSRM, Valhalla): the actual upgrade, because the honest limitation here is not the ordering — it is that these are straight-line distances. There is no road network, no one-way streets, no traffic. It is a planning aid, and the README says so rather than implying otherwise.

15Questions to be ready for

If you built this, these are the questions worth having an answer to. The answers below are prompts, not scripts.

Why MongoDB? Wouldn't Postgres be better for this?

Concede the point first — it is a strong one. Slots and sales are relational in shape, and Postgres would give real foreign keys, which this schema currently lacks. Then give the actual reason: four capabilities that would otherwise be four pieces of infrastructure come from one system here — time-series, geospatial, a change feed, and transactions. Naming what you gave up is more convincing than claiming the choice was free.

Walk me through what happens when a machine sends a heartbeat.

Five steps, in order: authenticate the machine by hashed API key with a timing-safe compare; validate with Zod and append to the time-series collection; denormalise the latest values onto the machine document; run the alert rules; and let the change stream on that write push to every connected dashboard. The point to land is step three — the denormalised copy is what makes the fleet list one query instead of one aggregation per machine.

How does the dashboard stay up to date?

It never polls. MongoDB change streams tail the oplog and the server forwards those to browsers over an authenticated WebSocket. The follow-up worth pre-empting: what happens when the stream dies. Answer that you track a resume token, reconnect with backoff, and push a health frame so the UI shows stale — because a green light over frozen data is worse than an outage.

Why do you need a replica set for a single-node database?

Because change streams and transactions are implemented on the oplog, and a standalone mongod does not keep one. It has nothing to do with redundancy here. Add that the app checks at boot and refuses to start otherwise, which turns a confusing silent failure into a one-line error.

How do you stop the same alert firing every 30 seconds?

A dedupe key of machine + type + subject, and a partial unique index scoped to alerts that are still open. Partial matters: the same fault can legitimately recur next month, so the constraint must not apply to resolved ones. It is enforced in the database rather than in application code, so two concurrent ingest requests cannot both create it.

What happens if the vend transaction fails halfway?

Both writes roll back. Explain why both matter in that direction: a decrement without a sale silently loses revenue, and a sale without a decrement makes the forecast believe in stock that is not there. Then mention what is deliberately outside the transaction — the alert rules — because a failed alert write must not undo a sale that physically happened.

It's deployed publicly. What stops a stranger breaking your demo?

Start by admitting the original mistake, because it is the more interesting half: the seed file hardcoded the admin password, and that file is in a public repository — so anyone who read it had admin on the live instance. Then the fix: a viewer role that can read everything and mutate nothing, enforced by requireWriteAccess on each route rather than by hiding buttons. The viewer password is public on purpose, because the role cannot do damage; the write-capable passwords are generated at seed time and never committed. The smoke suite attempts every mutation as a viewer and asserts a 403 plus an unchanged database — because a permission you have not tried to break is not a permission you know you have.

How is the AI grounded? What stops it making things up?

It cannot answer from memory — it only has six tools, all of which query the live database, and the UI shows the full tool trace beside the answer so an operator can check it. Then the security point, which is the one that lands: every tool is read-only by construction, so even a successful prompt injection can mislead a reader but cannot change fleet state.

Why isn't this on Vercel?

Lead with the fact that the obvious objection is stale — Vercel has supported WebSockets natively since June 2026. Then give the real reason: a socket is pinned to a function instance for its max duration and dies when that is hit, which on the Hobby plan is a hard 300 seconds. And more importantly, four things here hold state in the process — tickets, change stream resume tokens, the offline sweep timer, and rate-limit buckets — and none of them survive being spread across ephemeral instances. Finish with the version that does work: SPA on Vercel, stateful API somewhere with long-lived processes.

This is a portfolio project. Is it production-ready?

Answer this one straight, because hedging is what looks bad. Say what is done: authenticated everywhere, validated config that refuses unsafe production settings, resumable streams, security headers, a non-root container. Then say what is not, without being asked: it runs on one instance, because WebSocket fan-out and rate limiting are both in-process and Redis is the next real piece of work. Also no metrics, no backup procedure, and no unit tests beyond the 32 end-to-end ones. Knowing exactly where the line is is the answer.

What would you do differently if you started again?

Have two or three real ones ready. Candidates: put the fan-out behind Redis from the start rather than retrofitting it; use a targeted $inc on the slot rather than saving the whole machine document, which would remove a real concurrent-write risk; and build the forecast with day-of-week seasonality instead of a flat trailing average, because a flat average cannot see a holiday.
